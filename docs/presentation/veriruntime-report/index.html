02 / 22

三个角色的分工，是后面所有设计的基础。上层决定要证明什么，也承担语义内容的编写，比如前置条件、循环不变式和证明代码。运行时接收这些内容之后，只优化怎么执行：选工具、安排顺序、并行和回退。

执行后端更靠近基础设施，它接收已经选好的命令，负责进程生命周期和资源事实。后端没有 SAFE 这种结论，工具 adapter 才解释原始输出，运行时再按确认要求归并。当前可靠的验收入口，是固定 C 断言目标的多家族执行。

上层的请求先进入校验和源码快照，再形成逻辑目标。优化器读取工具资格和历史，为这个固定目标生成物理计划。引擎遍历计划，控制截止时间和并发，再把选好的命令交给执行后端。

VeriRuntime · veriruntime/model.py / veriruntime/plan.py
04 / 22

目标身份和执行身份需要分开。源码、入口、属性、数据模型以及确认要求构成目标的语义内容，它们发生变化，就不能沿用原来的结论。预算或标签变化，不等于命题变了，所以不进入 semantic_key。

物理计划是另一个对象：同一目标在不同机器、不同工具资格或不同历史下，可以生成不同的并行组合和回退顺序。每次调用又有独立的执行记录。缓存命中时仍建立新记录，并通过来源执行 ID 指向原始证据，不能只留下一个没有出处的 SAFE。

左侧是完整的 C 程序，右侧保留了真实 JSON 的全部字段，只调整排版。source 路径相对任务文件解析。请求要求 C11、LP64 语义下的断言安全，至少两个不同家族确认，总预算三十秒、两 GiB、最多并行两个工具。

这一步输出的不是文件名列表，而是内容快照。之后执行使用快照内的内容，避免源码在工具运行之间变化。真实例子把路径规范化为 c/safe_assert.c，并保存完整内容与 SHA-256。semantic_key 又把源码身份和目标语义、确认要求结合起来。

三十秒按两个阶段等分，每阶段十五秒。第一阶段并行运行 CBMC 和 ESBMC；第二阶段保留给 CPAchecker。本例两家族都给出了 SAFE，达到请求要求，因此引擎结束目标，后备没有启动。入选工具列表包含三者，实际 attempts 只有两个。

VeriRuntime · compose.yaml / veriruntime/tools/docker_api.py
10 / 22

控制容器只承担调度和存储，保留 Docker socket 以创建工具容器。每一次工具尝试只挂载属于自己的 volume subpath，到容器内的 work 目录；看不到另一工具的工作区，也看不到数据库或源 checkout。输入文件只读，缓存和临时目录各自独立。

这次请求两 GiB、最多并行两个，因此每个 worker 固定一 GiB，另有一 CPU 的 cgroup 限制。隔离防止验证结果污染，但共享宿主内核，也仍有控制层和 daemon 的额外成本；桥接进程的 RSS 不能当成 worker 的峰值内存。
